# 项目概述

## 项目目标

Hyperf DPoP 是面向 PHP/Hyperf 应用的 RFC 9449 服务端持钥证明扩展。它验证客户端对私钥的持有情况，将访问令牌绑定到公钥指纹，降低泄露令牌被直接冒用的风险。

项目采用一个开发工作区、两个 Composer 包：

| 包 | 目标与边界 |
| --- | --- |
| `lowelllab/dpop-core` | 独立于框架的证明验证、nonce、时间策略和防重放协调 |
| `lowelllab/hyperf-dpop` | Hyperf 集成、中间件、签发/刷新辅助器、存储驱动、共享预算、配置与诊断 |

业务项目只需要求安装 Hyperf 适配包，协议核心作为依赖自动安装。Composer vendor 使用 `lowelllab`，PHP 命名空间仍为 `Acme\Dpop`、`Acme\HyperfDpop`。

## 核心用户

- **业务开发者**：将 DPoP 接入已有 JWT 或不透明会话体系，实现可信令牌解析、账户校验和业务权限。
- **基础组件维护者**：维护协议、存储、接入契约、兼容性与双包分发。
- **部署与测试人员**：配置网关、HTTPS、共享状态与超时，执行真实宿主及目标拓扑验证。

## 系统边界

扩展负责 HTTP DPoP 验证，不提供完整 OAuth 授权服务器、账号系统、客户端 SDK、WebSocket 认证或 mTLS 证书管理。DPoP 证明不保护请求 body 和 query 的完整性，通信仍须 HTTPS。

| 边界对象 | 职责 |
| --- | --- |
| 客户端 | 保存会话私钥，构造 ES256 proof，处理 nonce 挑战并重新签名；资源请求计算访问令牌的 `ath` |
| 宿主身份系统 | 校验账号、签发/验证令牌、撤销会话、提供可信 `cnf.jkt` 或权威绑定；完成业务授权 |
| 宿主刷新事务 | 在证明通过后，以行锁或 CAS 复核旧凭据与原绑定，再执行轮换 |
| HTTPS 入口网关 | 检查重复认证头、拒绝认证 Trailer 声明、剥离实际尾部字段，向后端转发 HTTP/1.1 |
| MySQL | 默认权威防重放账本；使用专用连接、独立提交和唯一约束 |
| Redis | 默认跨 Worker/实例认证预算，以及显式选用的可选重放驱动 |

宿主会话/JWT 存储与 DPoP 账本是不同职责；包不要求宿主采用某个账号模型，也不自动迁移业务表。

## 核心业务流程

### 1. 持钥签发与刷新

宿主 token 入口调用 `TokenEndpoint::issuance()`，完成 proof、目标、时间、nonce 及重放验证；之后宿主才校验账号并创建绑定会话。刷新入口调用 `TokenEndpoint::refresh()` 检查原绑定，再由宿主原子复核和轮换。refresh token 不作为 `ath` 的计算对象，也不能借刷新自动更换绑定密钥。

### 2. 受保护资源访问

请求经过入口网关和受保护路由中间件，先取得有限认证预算，再检查原始/PSR 认证字段、解析可信访问令牌绑定、验证 proof、nonce 与时间并登记重放账本。认证成功后，将不可变 `DpopContext` 放入当前 PSR 请求属性，释放认证槽位，再交给宿主业务授权和处理。

### 3. 接入、诊断与维护

宿主显式发布配置、DDL 和网关模板，填写密钥、公开 origin、存储和 resolver。DDL 只复制，不自动执行；网关只提供模板，不自动部署。`dpop:doctor` 检查配置、绑定依赖、schema 与预算连通性，不执行真实认证或写入安全账本。
